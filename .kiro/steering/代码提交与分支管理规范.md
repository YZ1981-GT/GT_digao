# 代码提交与分支管理规范（GT_digao）

> 适用范围：本仓库为前后端同仓：`frontend/`（React 18 + TypeScript）+ `backend/`（FastAPI + Python 3.12）。
> 远端：`origin = https://github.com/YZ1981-GT/GT_digao.git`，默认分支 **`master`**。
> **红线：`master` 是受保护基线，禁止直接提交或推送；所有改动走工作分支 + Pull Request。**

## 一、当前仓库实际情况（以此为准）

- 仓库**没有** `.git-hooks/`、`push_version.py`、`check_git_branch_naming.py`，也没有 commitlint/husky。
  本规范靠人和 AI 自觉执行，**不存在自动硬门**；不要声称“钩子已检查通过”。
- 推送新提交直接用 `git push -u origin <工作分支>`，不打版本标签。
- 工作区经常存在用户自己的未提交改动：AI 提交时**只暂存自己的改动**，不得 `git add .` / `git add -A`，
  不得 `git stash`、`git checkout -- <file>`、`git reset --hard` 动用户的工作区。

## 二、分支

| 分支 | 命名 | 用途 |
|---|---|---|
| 基线 | `master` | 受保护，只通过 PR 合入 |
| 修复 | `fix/<topic>` | 缺陷修复（如 `fix/report-review-consistency`） |
| Spec 实施 | `spec/<spec-name>` | 对应 `.kiro/specs/<spec-name>/` |
| 单次工作 | `work/YYYY-MM-DD-<topic>` | 临时工作或验证 |
| 发布 | `release/v<version>` | 发布准备，只修 bug |

- 名称只用小写字母、数字、连字符；后缀要能看出做了什么（禁止 `fix/bug`、`work/test`）。
- 从最新的 `origin/master` 创建工作分支（先 `git fetch origin`）；若本地 `master` 有未推送提交，
  新分支会把它们带进 PR，需在 PR 描述中注明。
- 分支合并后删除。

## 三、提交信息（Conventional Commits）

格式：`<type>(<scope>): <subject>`，可带正文。

- `type`：`feat` `fix` `docs` `style` `refactor` `perf` `test` `chore` `build` `ci` `revert`
- `scope`：用端前缀区分：`web-<模块>`（前端）、`server-<模块>`（后端）、`root`（根目录配置）
  - 例：`fix(server-report-review): 确认科目匹配后保存会话`、`feat(web-report-review): 附注表格显示金额单位`
- `subject` 不超过 50 字，祈使句，结尾不加句号。

## 四、提交原则

1. **原子提交**：一个提交只做一件事；前端与后端改动分开提交，PR 描述中注明依赖。
2. **提交前验证**：后端 `python -m pytest tests -q`（cwd=`backend`），前端 `npx tsc --noEmit`（cwd=`frontend`）。
   若与用户未提交改动混在同一文件，应导出暂存区（`git checkout-index -a --prefix=<临时目录>/`）单独编译和测试，
   确认提交本身可运行，不能只看工作区结果。
3. **不提交**：密钥、`.env`、`node_modules`、构建产物、`backend/data/sessions/`、`backend/data/snapshots/`、`uploads/`。
4. 优先新建提交修正问题；只有在**未推送**且用户明确同意时才改写本地历史（合并/修改提交）。
5. 禁止 `--no-verify`、`push --force`（除非用户明确要求）。

## 五、Pull Request

- 用 `gh pr create --base master --head <分支> --title ... --body-file ...` 创建。
- 标题沿用提交格式，不超过 70 字。
- 描述包含：**背景、改动、自测（含未覆盖项）、影响范围**；注明 PR 中包含的非本次改动的提交。
- 至少一名 reviewer 批准后合入；合入后删除源分支。

## 六、检查清单

- [ ] 没有在 `master` 上直接提交或推送
- [ ] 分支名符合第二节
- [ ] 每个提交信息为 `type(scope): subject`
- [ ] 只暂存了自己的改动，提交本身已单独编译/测试
- [ ] 无敏感信息、大文件、运行时数据入库
- [ ] PR 描述写清背景、改动、自测、影响范围
